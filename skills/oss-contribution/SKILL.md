# 开源项目贡献

按用户当前要做的事选择阶段，每次只读取对应参考。给出仓库、Issue、方案或 diff 时，直接进入相应阶段。默认预算为两周内完成实现、测试并提交 PR。以用户指定的时间和技术背景为准。

| 用户手头的信息或请求 | 参考 | 本阶段交付 |
|---|---|---|
| 想找项目，尚无仓库 | [项目筛查](references/screen.md) | 以当天日期计算筛选窗口。列出满足健康度指标的仓库及证据 |
| 给了仓库或 Issue，想确定做什么 | [机会调研](references/research.md) | 核查最新活动、认领和关联 PR。列出候选方向并自己选定一个，给出改动入口和验收条件 |
| 已选方向，需要技术方案 | [方案设计](references/design.md) | 复核源码与测试，比较方案，估算工作量，产出维护者评论与面试叙事框架。定稿后直接进入实现 |
| 已选方案，要求本地实现 | [受控实现](references/implement.md) | 检查本地基线。接口定稿后直接接入逻辑、运行测试，回填叙事框架的验证结果 |
| 改动完成，要过审查 | [审查分级](references/review.md) | 判断谁能审：常规代码交无上下文子代理并行审，重要代码留给人，且先给心智模型再给 diff |
| 改动完成，要变成 PR | [提交链路](references/submit.md) | fork、分支、提交、推送、开 PR；CLA 与 CI 的处理规则 |
| 已有改动，需要 PR 文案 | [PR 描述](references/pr.md) | 根据实际 diff、已执行的命令和目标仓库模板写标题与正文，自检通过后直接发布，回填叙事框架的成果与复盘 |

机会调研时，针对单个 Issue 沿触发路径选读相关架构维度；用户要求完整调研，或需要从源码寻找方向时，逐项检查七个维度。记录日期、分支、SHA 和原始链接，将实测结果、源码推断、待核实项分开。

## 贡献任务卡

选定方向后，用[任务卡模板](assets/task-card.md)建立一张卡，存到 `~/.workbuddy/oss-contributions/<贡献 ID>/task-card.md`。跟踪上游项目时，这个目录必须在项目工作树之外。尚未选定方向时不建卡。

每次推进时更新这张卡，记录本阶段结论、对应证据和一个具体下一步。接续时先读卡，重新核查可能变化的 Issue 状态、认领和代码版本。沿用卡片里的决定和依据，除非新证据表明前提已经变了。范围发生变化时同时更新成功标准和预测改动量。

## 自主决策

全程不设人工确认节点。方向选择、方案取舍、接口设计、范围边界、发布与否都由你决定，决定完继续往下走，不停下来等回复。每个决定在任务卡里留三行：决定了什么、依据是哪条证据、放弃了哪些选项以及原因。证据不足时选可逆的一步——缩小范围、先补测试、拆成两个 PR——而不是选需要猜测的方案。

方案有遗漏、与现有代码冲突、两种做法各有利弊、需要新依赖时，按“改动最小、可回滚、不改变既有公共行为”的顺序自己选一条，把理由写进卡片。新依赖默认不引入。

### 停点判定

停下来问之前，先判断这件事能不能替用户做。**必须自己做**：选哪个项目或 Issue、方案取舍、范围大小、是否发布、以及任何形式的“要不要我继续”。这些问了就是违规。

**只有四类可以停，且停下时必须写明类别和一句理由**：

- **A 法律/合约**：CLA、DCO、许可协议、企业合规的**签署动作**不能代签。只挡签署，不挡开 PR——多数仓库在 PR 创建后才弹签署提示。
- **B 账号与凭据**：需本人交互登录、OAuth 授权、支付、修改账号设置；在项目之外的渠道（博客、社交媒体、个人主页）以本人名义发声。**在目标仓库内发 Issue 评论、开 PR 属于本 skill 的既定授权，不算停点。**
- **C 不可逆且影响他人**：删除、force push 到他人分支、修改或关闭他人的 Issue / PR。
- **D 信息缺口**：推进所需的输入只在用户手里（私有仓库权限、业务约束、只有他能确认的事实），且无法用可逆手段绕过。停下的形式是说清缺什么，不是问「要不要继续」。

说不出触发 A–D 中的哪一条，就不要停，做完再汇报。每次停顿都要在任务卡的“停点”一栏留记录，便于事后核对是否误停。

### 收尾自检

每轮结束前核对两件事，任一条不成立就继续做完再收尾：

- 本轮是否停下过。停过就确认任务卡「停点」里写明了 A–D 之一；写不出类别，说明是误停，补齐工作再收尾。
- 回复里是否出现「要不要我继续」「需要我现在做吗」「你想先看哪个」这类问句。有就删掉，改成已完成的事项 + 下一步依赖（仅当依赖属于 A–D 时才写）。

### 发布自检

评论和 PR 直接发布，不先交草稿。逐条核对，按两类处理：

**自己能补齐的，补齐再发：**

- diff 与要发布的内容逐条对应，没有夹带无关改动。
- 已声明的可验证项全部通过；无法验证的项在卡片「不可验证」里写清原因、对 PR 的影响和披露位置，并在 PR 正文如实说明。
- 语言与该仓库近期 Issue、PR 一致；不含夸大措辞、模板套话和未验证的结论。
- 不含密钥、绝对路径、内部主机名和他人隐私。
- 对照 `CONTRIBUTING.md` 的显式约束逐项核过：改动目录、PR 体量、截图或录制、声明段落。与文档不符时，在 PR 正文里先解释，不要等对方来问。

**自己补不齐的，转状态而不是重试：**

- 同一问题已有进行中或已合并的 PR → 台账记 `competitor-open` / `superseded`，回阶段二换方向。
- Issue 已被认领或已关闭 → 台账记 `closed-upstream`，同上。
- 需要本人签署或声明 → 台账记 `blocked`，写清缺什么、谁能解、解除后第一步做什么。

竞争检查要给三段证据，不能只搜编号：编号检索（`is:pr <issue> in:body`）+ 关键词检索（症状、报错串、改动文件名）+ 该文件近期 merged PR 列表，并在卡片记下检索式与检索时间。
- 发布后把链接、时间和内容摘要写进任务卡。

任务卡的 `publish` 写 `dry-run` 时只交付草稿；默认 `auto`，不写就按 `auto` 处理。

### 质量闸门

维护者的注意力是稀缺资源，不是你的产出量。每道闸没过的 PR 都在消耗以后的机会，所以下面五条按顺序执行，不过就不提交：

1. **可复现**：本地能重现问题，留下命令或截图。复现不了就不进实现，改成「读代码 + 写出会失败的用例」来证明缺陷，并在卡片标注复现程度（端到端 / 单元级 / 仅代码推断）。
2. **单一意图**：一个 PR 只解决一个问题，diff 控制在 300 行内，不夹带格式化、重命名、无关清理。
3. **测试先红后绿**：先写能失败的用例，再改到通过。只有「改完测试绿了」不算证据，那可能什么都没修。
4. **公共行为不变**：默认路径的输出与改动前一致（快照、逐字节比较或显式断言），或者明确写出行为变更及其理由。
5. **三句话说得清**：问题是什么、为什么这样改、影响哪些调用路径。说不清说明还没想清楚，不要靠 PR 正文遮掩。

提交前再站到维护者那边问三句：这是真问题吗（有复现）？我能在十分钟内 review 完吗（体量）？作者会回应吗（你自己的响应记录）？

闸门过了还要过审，按[审查分级](references/review.md)：能被测试或编译抓住的改动交无上下文子代理并行审；改变默认行为、跨边界、涉及权限或依赖的改动必须人审，且先给心智模型再给 diff，不能直接甩代码。

**数量纪律**：同一时间只推进一个 PR；同一仓库的第二个 PR 优先于新仓库的第一个——连续贡献是维护者眼里最强的信号，广撒网换来的是每条都停在「第一次打交道」。

## 面试叙事框架

方案设计启动时起草，之后随实现、测试、评审、合并逐步更新，作为这次贡献的可讲述版本。放在任务卡同一目录，在卡片里记录文件路径和最近更新时间。

根据当前进度填写。设计阶段使用“我已核实”“我比较过”“我计划”等符合事实的表述；实现、测试、评审和合并情况在取得证据后更新，没有证据的结论留空。

用户转述、但本人未核对的内容标注来源（如“用户陈述”），不要写成亲自实测。可能被追问的链接、数字和失败输出，补齐证据或改成可核实的说法后再对外使用。

把一条内容从待核实改成已核实，需要原始输出或链接；只有转述就保持待核实。定稿前自查：每条结论都能追到一条证据，追不到的删掉或降级为计划。不需要等人审阅这份材料。

### 1. 背景（Context）

- 项目在 AI Agent 的哪个使用场景中发挥作用？
- 我为什么选择这个贡献方向？哪个具体场景暴露了问题？
- 哪段调用链、哪个测试或哪条 Issue 记录支持我的判断？

### 2. 贡献（Contribution）

用一句话概括贡献，交代改动在项目中的位置和受影响的使用路径。设计阶段写拟实现的行为，提交后换成 PR 实际交付的内容。

### 3. 过程（Process）

按实际顺序组织 3～5 个关键步骤。每步讲清楚一个决定及其依据，例如：

1. 我怎样复现问题，并把改动范围缩小到某个调用点？
2. 我比较了哪些方案？哪项约束决定了最终选择？
3. 我怎样验证新行为，同时保留已有调用方依赖的行为？
4. 如果维护者提出修改意见，我根据什么证据调整了设计？

### 4. 成果（Result）

- **PR 状态**：设计中／已提交／审核中／已合并／已关闭。提交后附链接。
- **功能影响**：结合相同输入，说明修改前后的行为差异。
- **量化指标**：有实测数据时，给出基线、结果和测量条件。功能修复也可以用回归用例和关键断言展示成果。
- **维护者反馈**：收到评审后，引用一句与技术决策相关的原话，并附评论链接。

### 5. 困难（Challenges）

实现后挑选 1～2 个真实卡点，分别写明：

- **困难描述**：具体症状是什么？为什么难定位或难取舍？
- **排查过程**：我如何复现、检查了哪些证据、试过什么办法？
- **最终处理**：采取了什么措施？如何确认问题已经解决？

设计阶段可以记录预判的风险和验证计划，供实现后对照。

### 6. 复盘（Reflection）

- **技术层面**：结合实现结果，哪个设计决定值得保留，哪里有更简单的做法？
- **协作层面**：维护者在哪个时点介入最有帮助？PR 的拆分是否方便评审？
- **范围层面**：哪些改动可以省去？是否遗漏了重要边界？

### 7. 核心能力

选出这次贡献最能体现的 2～3 项能力。每项对应一个具体决定和一项证据，例如“故障定位 → 找到状态丢失的调用点 → 回归用例在修复前失败、修复后通过”。根据实际贡献填写。

## 产出归档与状态跟踪

产出不留在会话工作区，统一放在 `~/.workbuddy/oss-contributions/`：

- `ledger.json`：贡献台账。一条贡献一个对象，记录 `repo`、`issue`、`pr`、`branch`、`base_sha`、`stage`、`status`、`events`、`resume`。
- `check.py`：状态核查脚本。`python check.py` 只打印状态变化，`--all` 打印全部条目，`--id <条目>` 只查一条；`python check.py add --repo owner/name --issue 123 [--pr 456]` 新建条目并创建产物目录。依赖已登录的 `gh`。
- `<id>/`：该次贡献的任务卡、叙事框架、PR 正文、补丁。

### 何时写台账

- 选定方向、建立任务卡时：创建 `<id>/` 目录，在 `ledger.json` 追加条目，`status` 初始为 `not-submitted`。
- 阶段性推进时：更新 `stage`，并向 `events` 追加一条（日期 + 一句证据）。
- 发布 PR 后：写入 `pr` 与 `pr_url`，`status` 改为 `pr-open`。
- PR 合并后：补 `resume.bullet_zh`、`resume.bullet_en`、`merged_at`、`impact`——这部分是能写进简历的内容，缺了它这次贡献对外讲不出来。

状态取值：`not-submitted`、`competitor-open`、`superseded`、`closed-upstream`、`pr-open`、`changes-requested`、`merged`、`closed`。

台账跨会话存在，不随工作区变化。`last_checked_at` 与 `last_detail` 由脚本回填，不要手写。
