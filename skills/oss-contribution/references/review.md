# 审查分级：谁来审、审之前给什么

目标有两个，且互相牵制：快，和不漏。做法是把改动分成两类，走两条路——常规代码交给无上下文的子代理并行审，重要代码留给人，但**人看代码之前必须先拿到心智模型**。

## 一、先判断谁来审

### 人类必审（命中任一即升级）

- 改变默认行为、公共 API、配置项语义（哪怕只是加了个可选参数）
- 跨边界：序列化、导出、进程间协议、数据库结构、缓存
- 权限、认证、密钥、加密、脱敏
- 并发、异步、状态机、重试、超时
- 依赖增删或版本变更
- 删除或重命名公开符号
- 现有测试覆盖不到、只能靠人工推理的路径
- diff 超过 300 行，或触及超过 5 个文件

### 子代理可审

- 局部逻辑、纯函数、边界值与空值处理
- 新增测试、文档、注释、示例
- 命名、格式、类型标注、目录结构
- 与既有模式一致的重复性改动

判断口诀：**这个改动错了，能不能被现有测试或者编译直接抓住？** 抓得住 → 子代理；抓不住 → 人。

## 二、子代理审查协议

子代理没有上下文，材料必须自包含，否则它只能给出泛泛而谈的建议。

必须给的东西：

- 仓库绝对路径、基线 SHA、分支名
- 补丁文件路径（`git diff` 输出），不要让它自己找
- 这次要满足的验收标准（哪几条断言必须成立）
- 相关测试命令，以及哪些跑了、哪些没跑
- 明确要求：只读，不修改任何文件

必须要求的输出格式：按「阻断 / 影响 / 建议」三档，每条给 `文件:行号`、原文摘录、为什么是问题、建议改法。

拿到结果后由我复核：每条要么亲自验证，要么在卡片里标注「未验证」，不能直接当结论用。子代理会编造看似合理的问题，这一点必须防。

## 三、人类审查包

给人看代码之前，先给这六段，控制在一屏以内。目的是让人有判断力，而不是一头扎进 diff。

1. **系统怎么运转**：三到五句话 + 一条数据流（输入 → 哪几层 → 输出）。不写这段，后面全是无根之木。
2. **问题在哪一环**：具体到 `文件:行`，说明这一环为什么会错。
3. **改了什么、为什么改这里**：一句话总结改动，再说明为什么不动上游或下游。
4. **会波及谁**：哪些调用方、哪些语言版本、哪些用户路径。
5. **需要你判断的 2–3 个问题**：写成具体取舍，不要写「帮我看看有没有问题」。
6. **验证到哪一步、没验证什么**：跑了哪些命令，哪些没跑、为什么。

反例：甩一个 diff 说「帮我审一下」。这样得到的只会是格式和命名意见，真正的设计问题没人能提。

## 四、审查之后

- 子代理提的问题：逐条确认或驳回，驳回写理由，记进任务卡。
- 人类提的问题：原文记进任务卡，作为后续改动的依据。
- 属于「人类必审」的改动，未经人审就提交，一律视为未完成——不管测试多绿。
