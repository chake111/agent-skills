# 阶段一：项目筛查

目标：把「想贡献」变成一个具体仓库，并留下能复查的证据。

## 输入

- 用户给了领域或技术栈：按它检索。
- 用户没给：两条降级检索都跑，合并结果。
  1. 技术栈反查：`language:{用户主语言} topic:ai-agent stars:>500 pushed:>{30 天前}`
  2. 新手友好反查：`label:"good first issue" state:open`，再用 stars 过滤掉玩具仓。
- 用户直接给了仓库：跳过本阶段，进机会调研。

## 淘汰指标（任一不满足就丢弃）

- 最近提交：近 1 个月内有实质性代码提交。
- Issue 关闭率：Closed / Open > 1。
- PR 响应：近期 PR 一般在 2 周内有维护者 review 或回复。
- 发版频率：每月或每季度有正式版本。
- **贡献门槛**：读默认分支的 `CONTRIBUTING.md`、`.github/`，记下 CLA/DCO 要求、AI 辅助声明要求、允许改动的目录、是否要截图。读不到就标「未知」，不要假设没有。
- **本地可运行性**：按 README 能不能在半天内跑起来（外部依赖、镜像体积、必需的密钥）。跑不起来的不淘汰，但成本要写进表里，它决定后面能不能验证。
- **外部贡献者合并率**：取最近 20 个已合并 PR，数其中有多少来自非核心成员（`author_association` 为 `CONTRIBUTOR` / `NONE`）。低于 30% 说明这个仓库的 PR 主要靠自己人，外人提的基本在原地等。这一项比 stars 更能预测你的 PR 会不会被看见。

## 固定输出

每个候选仓库填一行，证据列贴原始链接或命令输出：

| 仓库 | Stars | 最近提交 | 关闭/开放 | PR 响应 | 发版 | 语言 | 本地成本 | 外部合并率 | GFI 数 | 贡献门槛 | 证据 |
|---|---|---|---|---|---|---|---|---|---|---|---|

## 出口

按「本地成本 < 半天」优先、再看「外部合并率 > 30%」「未认领 GFI 数 > 0」，自己选 2～3 个写进任务卡，直接进入机会调研，不交付清单等确认。

要交付清单，只在两种情况下：用户明确要一份横向对比，或者所有候选都不满足淘汰指标（此时说明每条卡在哪一项）。
